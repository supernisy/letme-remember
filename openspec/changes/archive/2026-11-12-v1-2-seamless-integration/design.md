## Context

letme-remember 当前是手动 CLI 引擎：`record`/`recall`/`consolidate` 都靠人主动敲命令，与宿主 Agent 的日常对话脱节。v1.1 已交付的 `batch_distill` + `consolidate` + 三级审批判定链（L0/L1/L2）是完整的「写」能力，但缺「何时触发写」「如何无感接入宿主」「写入前如何异步确认」这三层。本 change 的动机见 proposal.md「Why」。

关键既有约束（本设计必须遵守，不能破坏）：
- 文件即真相源，SQLite 索引是可重建缓存，私有 git 是审计账本。
- 读路径零网络、零模型调用。
- 裁决权在代码（固定阈值），LLM 只产报告不打分拍板。
- 所有写入可撤销（git 提交粒度）。

## Goals / Non-Goals

**Goals:**
- 把「会话开始注入、会话结束蒸馏」从手动变成宿主事件自动触发，用户无感。
- 蒸馏候选按 L0/L1/L2 分流：L0 静默入库，L1/L2 进待审队列异步确认，绝不静默丢弃。
- 一套核心引擎服务多宿主，宿主差异只存在薄适配层。
- 记忆数据加密后云端同步，密钥不上云。

**Non-Goals:**
- 不做向量语义检索（后续独立线）。
- 不做输出策略层（对外口径独立于记忆）。
- 备份不做分布式强一致，只做加密后的定期/实时弱一致同步。
- 不重写 v1.1 的蒸馏与判定链，只在其外围加「触发」和「确认」两层。

## Decisions

### D1：写入时机 = 会话结束触发（SessionEnd/Stop），后台异步执行

**选择**：蒸馏挂在宿主会话结束事件，后台异步跑，默认不实时。

**为什么**：业界共识（Mem0/Memory Bank/agent-memory/robinlg）都是「边界触发」，会话结束最经济、对话中提炼不可靠（此刻无法预知未来问什么）。异步执行不阻塞用户下一轮输入、不占主对话 token（claude-code-auto-memory 的独立 subagent 模式）。

**备选**：每 N 轮触发（成本/质量折中，但实现更复杂、边界不稳定）；实时每轮触发（贵且噪声大）。均不采用，但阈值控频（累计 N 会话或 M 天才跑一次）作为会话结束触发的补充开关保留。

### D2：写入前确认 = 待审队列（Approval Queue），非阻塞弹窗

**选择**：L0 静默入库；L1/L2 进待审队列（pending 状态、可审计），用户异步批量审批。确认载体以「集中待审清单（queue 命令）」为主、对话顺带提醒为辅。

**为什么**：这正是你点出的「无感 vs 不错过」矛盾的业界解（Approval Queue 模式）。阻塞式确认会把对话打断成"每轮点一次"，用户疲劳后变成橡皮图章；纯静默又会导致 L1 值得记的记忆被错过。队列方案的关键不变式：**待审项绝不自动执行**，用户不表态就保持 pending，超时降级 archive——既无感，又不丢。

**备选**：阻塞式同步确认（打断对话，否决）；静默全自动（L1 风险高，否决）；对话中自然带一句为主（易被淹没、不可靠，降为辅）。

### D3：超时兜底 = 降级暂存 archive，不静默丢弃

**选择**：待审候选超时（默认 7 天）从队列移至 archive 冷存储，保留完整内容，可恢复。

**为什么**：保守原则——「不替你决定」。降级到 archive 而非静默删除，保证任何值得记的内容都留痕、可捞回。这也呼应你「用户始终不表态就一直追问」的要求：追问无果后不是丢弃，而是安全暂存。

**备选**：超时自动入库（替用户拍板，违背「写入前征得同意」，否决）；超时静默删除（直接丢，否决）。

### D4：宿主集成 = 核心引擎不变，新增薄适配层 `lmr/host/`

**选择**：核心 `lmr` 引擎不动，新增 `lmr/host/` 目录，每宿主一个适配器（WorkBuddy 优先，DSH 随后），统一 `on_session_start`/`on_session_end` 接口；`mem.py setup --host <name>` 自动安装 hook 到宿主配置。

**为什么**：对标 agent-memory 的 `mem setup --host`（一套核心库 + 每宿主薄安装器）和 Claude Code 生态的 hook + subagent 模式。宿主差异（事件名、载荷格式）全部隔离在适配器内，核心引擎看到的是统一接口，符合既有 `cli` spec「多宿主接入同一份记忆仓库」的定位。

**备选**：为每个宿主写独立集成逻辑（重复、难维护，否决）；把记忆逻辑直接写进宿主（违背"引擎与宿主解耦"，否决）。

### D5：写入链路复用 v1.1 判定链，只加「触发 + 确认」两段

**选择**：会话结束 → 后台调 `batch_distill` 产出候选 → 代码分级（复用 L0/L1/L2 阈值）→ L0 直接 `store.record` 入库、L1/L2 写入待审队列 → 用户审批后 apply。

**为什么**：v1.1 的蒸馏、冲突检测、分级裁决、时间守卫都已验证（88 项测试），重写是浪费且引入回归风险。本 change 只需在判定链的外围加「谁在什么时候触发它」和「L1/L2 的结果如何异步确认」。

### D6：备份 = 本地加密 + 密文上云 + 密钥分离

**选择**：本地用 `age`（或 `cryptography`）加密数据目录 → 密文同步到云端（GitHub 私有仓库 / rclone crypt 挂载的网盘）→ 密钥留本地，绝不随密文上传。支持定期（cron/定时）与实时（rclone sync）两种。

**为什么**：业界标准「端到端加密 + 密钥不上云」。密文泄露不可解，本地丢失可用本地密钥恢复。复用既有 git 私有仓库，成本最低。

**备选**：明文上云（泄露风险，否决）；自研加密协议（重复造轮子，否决）；Syncthing 端到端 P2P（实时强，但需两台设备在线，作为实时选项而非默认）。

### D7：密钥红线在写入链的位置

**选择**：待审队列的候选在「批准 → 入库」时，仍走完整的 `store.record` 写入链（含第一审脚本校验 + 密钥形状红线硬拦）。L0 静默入库同样走完整链路。

**为什么**：待审队列只是"延迟了写入"，不是"绕过了校验"。任何最终落到真相源的内容，都必须经过 v1 就有的脚本红线（密钥打码）与 v1.1 的分级裁决，不能因为"已经审批过"就跳过安全闸门。这保证审批流不会成为红线绕过的后门。

## Risks / Trade-offs

- **[R1] 后台蒸馏延迟 → 记忆可用性滞后**：会话结束后才提炼，用户下次会话前若蒸馏未完成，可能拿不到刚产生的记忆。→ 缓解：蒸馏在会话结束立即触发（非定时），且注入读的是"已入库"的真相源，未完成的最多延迟一个会话周期；后续可加"会话结束同步等待一个短超时"的选项。
- **[R2] 待审队列积压 → 审批疲劳**：L1 候选多了，用户懒得批。→ 缓解：复用 L0 静默入库兜住大部分低风险；L1 批量审批 + 定期提醒（不强制）；阈值可调。
- **[R3] 多宿主 hook 注入的可靠性**：宿主事件机制各异，hook 可能没生效或静默失败。→ 缓解：`setup --host` 幂等且带自检（安装后验证 hook 已注册）；适配器失败只记日志不影响宿主对话。
- **[R4] 备份的密钥丢失 → 数据无法恢复**：密钥丢了，云端密文等于废。→ 缓解：文档明确"密钥需离线备份（U 盘/密码管理器）"；恢复流程显式检查密钥存在性。
- **[R5] 密文同步的一致性**：定期同步窗口内本地崩溃会丢最近增量。→ 缓解：实时同步（rclone sync）作为可选；定期同步默认每日，窗口内风险可接受。
- **[R6] 后台进程生命周期**：异步蒸馏进程可能随宿主退出被杀。→ 缓解：蒸馏任务持久化到队列/日志，宿主重启后可从断点续跑（幂等）。

## Migration Plan

1. 本 change 纯增量，不改 v1.1 已交付的蒸馏与判定链，无数据迁移。
2. 部署顺序：先 `lmr/queue.py`（待审队列，纯本地、零风险）→ `lmr/host/`（宿主适配，WorkBuddy 优先）→ `lmr/backup.py`（备份，可选依赖）。
3. 回滚：各模块独立，可分别 revert 对应提交；待审队列与真相源隔离（队列在 `proposals/`，不碰 store），出问题可直接清空队列不影响已入库记忆。
