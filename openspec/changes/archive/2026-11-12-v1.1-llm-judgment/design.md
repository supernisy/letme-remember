## Context

v1 已交付最小闭环：文件为真相源、SQLite 为可重建检索缓存、私有 git 为审计账本，写入走「打码 → 校验 → 落盘 → git 提交 → 增量索引」。v1 把「大模型软判断」留成了接口，用纯规则产出体检报告，冲突检测只能靠显式关联字段近似。

v1.1 要接入真实 LLM 做第二审（软判断），但**裁决权始终归代码**。约束：读路径零网络（检索不调模型）、公开仓库不发布真实 key、LLM 不可用时流程照常降级。

## Goals / Non-Goals

**Goals:**
- 把软判断从「占位接口」落实为「可插拔 LLM 提炼器 + 固定阈值裁决」。
- 冲突检测显式判定 ADD / UPDATE / SUPERSEDE / NOOP，与时间轴联动。
- 存量旧记忆用 LLM 批量蒸馏，替代手工一条条拆。
- 蒸馏产物质量可控：强制 JSON、Few-shot、打分截断、双轨（结论 + reference 索引）。

**Non-Goals:**
- 不做向量语义检索（仍是 v1.1 之后的另一条线）。
- 不做输出策略层、跨设备同步、后台维护进程、UI。
- 不做自动双向同步（与宿主平台记忆仍是单向只读导入）。

## Decisions

**D1：裁决权在代码，模型只产报告。**
LLM 产出结构化体检报告（六触发器 + importance/confidence/missing），代码按固定阈值映射 L0/L1/L2。替代方案是让模型直接输出「要不要人审」的布尔值——被否，因为模型输出不稳定、可被提示词诱导跳过审批，把裁决写死在代码里才能保证「审批不被模型跳过」。

**D2：可插拔 OpenAI 兼容客户端。**
通过配置指定 base_url / model / key，默认不连网、不依赖特定厂商。替代方案是硬编码某个厂商 SDK——被否，因为 key 会换、厂商会变，OpenAI 兼容协议是事实标准（百炼、DeepSeek 等国产均兼容）。Anthropic / Gemini 是独立协议，不在本次适配范围。

**D3：冲突字段升级为对象 `{ids, action}`，显式判定四动作。**
替代 v1 的布尔冲突。判定口诀「能并存 = UPDATE，不能并存 = SUPERSEDE」。四动作与时间轴联动：NOOP 自动丢、ADD 自动入、UPDATE 自动更（旧条靠时间轴保留）、SUPERSEDE 停下待人批。

**D4：SUPERSEDE 加时间维度守卫。**
批量导入旧记忆时，蒸馏出的「旧的大杂烩」可能被判为要取代库里「今天刚确认的精确结论」，方向反了。新增 `supersede_time_guard`：候选 `original_date` 严格早于被取代条目 `valid_from` 时，禁止取代，降级为 NOOP。替代方案是只靠 prompt 提示模型注意时间——被否，因为 prompt 是软约束，方向性误判必须用代码硬拦。

**D5：蒸馏双轨（结论 + reference 索引）。**
具体面试/事件/报告不蒸成结论（会丢案例细节），而是产 `reference` 索引指向原始档案，原文完整保留。替代方案是「把案例也蒸成结论」——被否，因为结论化会丢失具体问答/分析，用户明确要求案例可回溯。

**D6：reference 路径由代码回填，LLM 不猜路径。**
LLM 只写文件名，代码从真实文件系统（全盘文件名索引）回填绝对路径。替代方案是让 LLM 直接产路径——被否，实测 LLM 会编造文件名导致死指针（回填率 9%→64%）。路径失效时运行时按文件名重新解析，找不到就如实报「找不到原文」，绝不编造。

**D7：蒸馏质量三件套。**
① `response_format=json_object` 强制 JSON，减少畸形输出；② Few-shot 正反例教模型「什么该产、什么不该产」；③ importance 打分（1~5）+ 代码层截断（<3 丢弃）。替代方案是「软性后悔话术」（提示词里写「删掉会不会后悔」）——被否，因为软约束不可靠，改为「模型打分、代码按阈值砍」的硬机制。

**D8：分类判断交 LLM，不做正则枚举。**
批量蒸馏的「结论 vs 流水」分类，替代 v1 的正则枚举。正则枚举与任务不匹配、且应是句子级而非文件级。保留密钥值排除（密钥不能送 LLM，这是安全边界）。

**D9：蒸馏入口强制导入三字段完整性。**
蒸馏/批量导入候选带任一导入字段（source_category/original_date/batch）就必须三字段齐全，入口拦截。避免缺字段候选漏到落库阶段才爆、中断整批。

**D10：降级路径。**
LLM 不可用（未配 key、调用失败）时，退回 v1 的规则体检报告，流程照常，只是判断力降低。保证系统在无网络/无 key 环境下仍可用。

## Risks / Trade-offs

- [蒸馏质量依赖模型能力] → Few-shot + 打分截断 + 克制原则三重约束；实测纯流水账蒸出 0 条，噪声可控。
- [LLM 可能编造文件名/路径] → 路径由代码回填，LLM 只写文件名；找不到就明说，不编造（D6）。
- [SUPERSEDE 方向性误判] → 时间维度守卫硬拦（D4）。
- [缺字段候选中断整批落库] → 入口强制校验（D9），漏网候选在写库前即被拦。
- [key 泄露风险] → 公开仓库不发布真实 key，key 走私有数据目录或环境变量；敏感词隐私扫描门禁兜底。
- [读路径性能] → 检索只走本地 SQLite，零网络零模型，读路径测试收窄验证无外部依赖。
