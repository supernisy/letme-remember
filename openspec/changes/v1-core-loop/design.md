## Context

- 仓库现状：6 个能力规范已通过 `openspec validate --specs`（零警告），但没有任何实现代码；本次是第一个变更提案。
- 需求边界来自《需求定稿》§6：不自动写入、不自动淘汰、不做真知识图谱、不做 UI、不存会话原文语料、不做新旧记忆双向同步。
- 参考实现 `tigerless-labs/agent-memory` 的源码已读完，只借鉴设计决策，不 fork；fork 与否仍挂起。
- 本机实测：Python 3.13.14、SQLite 3.53.1、FTS5 可用；未装 ollama，所以向量检索放 v1.1。
- 本机实测：PyPI 可达（`pypi.org` 返回 200，约 0.2 秒），国内镜像亦可达；`github.com` 网页域名不通只影响代码推送，不影响安装 Python 依赖。相关库当前均未安装。
- 本机实测：SQLite FTS5 默认 `unicode61` 分词器把整句中文当成一个词，中文查询「记忆」「真相源」均零命中；`trigram` 能命中三个字以上的词，两字词零命中。中文检索必须做预分词。
- 本仓库是**公开**的，而记忆条目会包含真实私人信息。因此代码与数据必须分离，这条优先级高于一切便利性。
- 存量记忆分散在用户级规则文件、工作区日志与跨会话结论、身份文件、项目过程文档、求职过程档及备份等多个异构落点；形态与粒度均不一致，且含互相覆盖与过期结论。本次只为其预留字段语义，不执行导入。
- 网络现状：`github.com` 网页域名直连不通、`api.github.com` 通；这不影响本地实现，只影响以后推送。

## Goals / Non-Goals

**Goals:**
- 让「写入一条结论 → 关键词查得到 → 按日期查历史真相」在本地完整跑通。
- 把第一审（脚本校验 + 红线）、时间轴、可撤销审计做成硬约束，不靠人自觉。
- 让多个宿主面对同一份格式契约，避免各自写出不同方言。
- 运行时依赖控制在最小白名单内，且任一依赖缺失时功能可降级、不瘫痪。
- 让存量记忆导入所需的来源与原始时间语义在文件头里有确定的写法。

**Non-Goals:**
- 不接本地 embedding / 向量检索（v1.1）。
- 不实现输出策略层（同一敏感事实按人/场景取不同口径），这是后续独立提案。
- 不执行存量记忆导入，也不做新旧记忆的双向同步；导入另立提案。
- 不实现自动写入、自动淘汰、后台维护进程。
- 不做 UI、不做云端同步、不做真知识图谱。
- 不把任何真实记忆数据放进公开代码仓库。

## Decisions

**D1 运行时依赖策略：白名单 + 可降级。**
- 实现语言为 Python 3；标准库承担文件头解析、字段校验、命令行、git 调用与 SQLite 索引。
- 白名单内只有一个运行时依赖：中文分词库（纯 Python、自带词典、无需编译）。PyPI 与国内镜像均实测可达。
- 该依赖缺失时 SHALL 自动降级到 SQLite 内置 `trigram` 分词 + 两字短词 `LIKE` 兜底，检索仍可用。
- 明确不纳入：命令行框架（标准库 `argparse` 足够覆盖六个命令）、数据校验框架（会做隐式类型转换，与 D8 封闭文件头冲突）、重量级语义识别框架（依赖 NLP 模型，与本地轻量定位不符）、向量相关库（v1.1 再评估）。
- 红线检测不引第三方扫描器，规则表自行维护（见 D9）；业界扫描器的插件式规则、熵检测与误报白名单思路被借鉴。
- 理由：中文检索质量由分词决定，而非检索引擎；一个可降级的纯 Python 依赖，其收益远大于接入成本。

**D2 入口形态：单文件命令行 `mem`，不做界面。**
理由：《需求定稿》§6 明确 v1 不做 UI，审批以「大模型回复 + 脚本」的形式进入。命令式入口天然可被任何宿主调用。备选：做成库/SDK（宿主还得自己封装，v1 不必要）。

**D3 代码与记忆数据分离（关键）。**
- 公开代码仓库：只有代码、规范、测试、一份**完全虚构**的示例记忆。
- 记忆数据目录：默认在代码仓库外，可通过配置或环境变量指定；内含 `store/`、`archive/`、`MEMORY.md`、`.index/`，并**在该目录内单独初始化一个私有 git**。
- 理由：仓库公开，而记忆条目含真实私人信息；靠「提醒自己别提交」是软约束，必须靠物理隔离当硬护栏。这也让「git 作为审计日志」继续成立——审计提交落在数据目录的私有 git 里，不进公开仓库。
- 备选：数据目录放进仓库但用 `.gitignore` 排除（忽略规则可能被误改，`git add -A` 也有风险），不选。

**D4 三审在 v1 的落地方式。**
- 第一审（脚本格式校验 + 形状规则红线，见 D9）：**完整实现**，纯代码、零模型调用。
- 第二审（大模型提炼候选）：做成**可插拔的提炼器接口**——仓库本身不内置任何模型调用；宿主可注入提炼器，未注入时由人直接提交候选。无论哪条路径，候选都必须过第一审，且**绝不直接落库**。
- 第三审（人审批）：内容变更类操作（合并/拆分/取代/删除/改摘要）先生成**提案文件**，人确认后由脚本应用；「哪些操作必须审批」写死在代码的分类表里，**不由模型临时决定**，且每类操作有单次数量上限。
- 理由：v1 最小闭环不引入模型依赖，同时保住「模型只产候选」「审批触发由脚本决定」两条硬约束。备选：v1 就接大模型（引入网络与不确定性，且 v1 没有边界触发蒸馏的需求），不选。

**D5 时间轴与失效。**
文件头存 `valid_from` / `invalid_at` / `superseded_by`；默认检索过滤失效条目，`--as-of 日期` 可查该时点的真相；失效与归档都不物理删除文件。理由：直接对应《需求定稿》§2.7 与 governance 规范的「永不物理删除」。

**D6 索引是可重建缓存。**
SQLite FTS5 单库 + 每条文件的「内容哈希」做增量同步；中文预分词结果单独存一个索引列；索引目录不入库；`rebuild` 删索引后从真相源重建，必须幂等且零知识丢失。理由：对应 storage 规范「索引层与真相源解耦」。

**D7 审计用 git。**
每次成功写入/维护在**数据目录的私有 git** 里产生一次提交，提交信息带操作类型与时间，可 `git revert` 撤销。理由：对应 governance 规范，不另造日志系统。

**D8 文件头格式封闭。**
自造极小的 frontmatter 读写器：只认固定字段集合、只认固定写法，遇到未知字段或富格式**直接拒绝**，不做任何隐式类型转换（不引入 YAML/JSON 解析器）。理由：多宿主与人共同读写，格式越封闭越不会被悄悄曲解。

**D9 第一审形状规则集（三层）。**
- **A 类「凭据与密钥」→ 强制打码，无例外**：已知厂商密钥前缀（AWS / GitHub / Slack / Google / Stripe / OpenAI 等）；私钥块（PEM 头及整块内容）；令牌结构（三段式 JWT、OAuth client_secret、Bearer 与会话令牌）；带凭据的连接串（`postgres/mysql/mongodb/redis` 等 `://user:pass@host`）；通用密钥赋值（`api_key|secret|password|token|passwd|auth` 后接值）；高熵串（Base64/Hex 熵阈值 + 长度下限 + 白名单）。
- **B 类「机器可读标识符」→ 默认告警、打码可配置**：带校验和的卡号、IBAN、邮箱、手机号、IP（v4/v6）、MAC、UUID、加密货币地址、URL 中的凭据参数。理由：这类值可能是记忆正文的一部分，一刀切打码会破坏记忆完整性；代码与数据已分离（D3），本机留存风险可控。
- **C 类「叙述性私人事实」→ 不进脚本、照常入库**：人名、地名、组织、个人经历等只能靠上下文识别，形状规则拦不住；对外口径由输出策略层负责（后续提案）。
- 处置顺序：形状匹配 → 校验和 / 熵复核 → 查误报白名单 → 打码或告警 → 在审计记录里标注命中的规则编号，不记录原值。规则表与白名单是纯数据文件，可版本化、可人工修。
- 理由：把「能靠形状判定的」全部收进脚本，把「只能靠语义判定的」明确留给输出策略层；两层边界清晰，且「敏感事实可入库」这条已定决策不受影响。

**D10 中文检索与分词。**
- 一手工程复盘的量化结论：约 4000 条中文查询下，SQLite FTS5 `trigram` 原生约 99% 返回空结果；做中文预分词后，检索质量回到可用区间，单次检索约 77 毫秒。决定质量的是分词，不是检索引擎。
- 因此：写入索引前先做中文分词，用空格拼成索引文本；查询端 MUST 使用同一套分词器、同一版本，否则会出现「写进去却搜不到」。两字短词走 `LIKE` 兜底；分词依赖缺失时按 D1 降级。
- `trigram` 的索引体积约为原文 2–3 倍，本地条目规模下无感，但仅在降级路径使用。

**D11 存量记忆导入的边界与字段预留。**
- 导入是**单向只读蒸馏**：源只被读取，不改写、不删除、不重建宿主既有记忆文件；日志流水、过程推演、重复备份、会话原文不进仓库，只提炼结论级条目。理由：存量本身含互相覆盖与过期结论，整搬等于把「分不清真相」原样复制进新仓库，且违反「不存语料」。
- 导入产出的是候选，SHALL 照过三审；冲突不自动裁决，生成取代链提案交人确认；一个导入批次在私有 git 中可整体撤销。
- 文件头语义在本次落地：`provenance` 记来源类别、原始日期与导入批次；`created` 为导入时间、`valid_from` 为原结论成立日期、`author` 为导入来源标识。三者 SHALL NOT 混用，否则时间衰减会把旧结论当成新写入，或让全部存量一次性沉底。
- 不做新旧记忆双向同步：双写会重新形成多个真相源。写入口何时切换另立提案。
- 导入本身不在本次范围：v1 尚无真相源与写入链可落点，等 `v1-core-loop` 归档后另立提案执行。

## Risks / Trade-offs

- **数据目录在仓库外**：优点是隐私硬隔离；代价是「克隆仓库 ≠ 拿到记忆」，宿主必须自己配置数据目录路径，示例与真实数据可能不同步。用一份完全虚构的示例数据加一份配置模板缓解。
- **第二审降级为可插拔接口**：保住了三审的骨架，但「自动提炼」能力要等后续提案。这是「最小闭环」与「完整三审」之间的取舍，需在审阅时确认。
- **纯关键词检索**：换个说法可能漏召回；显式分类/标签与 `--as-of` 可补一部分，语义检索留 v1.1。
- **一个可降级的运行时依赖**：多宿主接入时仍需各自安装中文分词库；未安装时检索质量下降但不瘫痪。依赖声明固定版本，避免写入端与查询端的分词结果随版本漂移。
- **形状规则误报**：高熵串与通用赋值模式容易误伤普通长串（如哈希、示例值）；用校验和复核、误报白名单、「只标注不拒绝整条记忆」控制。B 类标识符默认只告警，不打断写入。
- **公开仓库**：任何示例、注释、测试用例都必须用虚构中性内容，不能出现真实私人信息或凭据。
- **存量数据自带冲突**：旧记忆里同一主题可能有多条互相覆盖的结论，导入时不能靠时间戳或相似度自动判谁有效；由「只产候选 + 人审批」兜住，但这也意味着导入不是一次脚本批量拷贝，而是分批的人工确认过程。
