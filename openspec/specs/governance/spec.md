# governance

## Purpose

定义记忆的长期治理：淘汰策略（不是 TTL 硬删，而是时间衰减 + 权重 + 手动归档）与审计追溯（复用 git 作为 trace）。

## Requirements

### Requirement: 永不物理删除

记忆文件 SHALL 永不物理删除，只标记失效 + 归档。

#### Scenario: 记忆失效不删除
- **WHEN** 一条记忆失效
- **THEN** 系统标记其失效（invalid_at），而非删除文件
- **AND** 失效记忆默认不进入检索结果

#### Scenario: 归档离开检索面
- **WHEN** 失效记忆需要彻底移出检索
- **THEN** 系统将其归档到 archive 目录，文件仍在磁盘、可追溯

### Requirement: 淘汰三结合

淘汰 SHALL 不是 TTL 硬删，而是「时间衰减 + 权重 + 手动归档」三结合。

#### Scenario: 淘汰机制
- **WHEN** 系统评估记忆去留
- **THEN** 综合三股力：
  - 时间衰减（越旧越沉底，自动）
  - 权重（重要记忆衰减慢、排名靠前，人工介入）
  - 手动归档（用户主动归档，彻底离开检索）

### Requirement: 淘汰只做提案

自动淘汰 SHALL 不直接执行，只做「提案」，需人确认。

#### Scenario: 淘汰提案
- **WHEN** 某记忆权重降到下限、建议淘汰
- **THEN** 系统只生成「淘汰提案」，MUST 经人确认后才生效，不自动删

### Requirement: 上游缓存 / 下游权威（单一真相源）

letme-remember SHALL 与宿主 Agent 平台的内置记忆构成「单向上下游」，不做平行系统：宿主平台记忆为上游现场缓存，letme-remember 为下游权威沉淀层，数据只单向流入下游，下游不反向回写上游。同一事实的「当前生效真相」由下游通过时间轴 + 取代链唯一确定，冲突不靠并列两套记录解决，而靠把并列关系变成先后关系。

#### Scenario: 冲突靠取代链收敛
- **WHEN** 同一事实存在先后两条相反结论（如旧结论「只看杭州」、新结论「可接受上海」）
- **THEN** 新结论写入时旧的 MUST 标记 superseded_by 失效
- **AND** 检索 MUST 只返回最新生效那条，旧结论不参与裁决

#### Scenario: 上游不反向写回
- **WHEN** 宿主平台记忆与 letme-remember 结论冲突
- **THEN** 以「用户本人 + 下游权威」为准，上游缓存不反向写回下游、不参与定义真相

#### Scenario: 只读导入为单向入口
- **WHEN** 把宿主平台已积累记忆导入下游做存量
- **THEN** 导入 SHALL 为单向只读蒸馏，不建立双向同步、不反向推送

### Requirement: git 作为审计日志

系统 SHALL 复用 git 作为 trace（审计日志），可查谁改的、何时改的、改了什么，可撤销。

#### Scenario: 维护动作产生 commit
- **WHEN** 系统执行一次维护（写入、修改、归档等）
- **THEN** 在 git 仓库中自动产生一次 commit，作为审计记录

#### Scenario: 审计查询
- **WHEN** 用户需要排查「某条记忆什么时候被谁改的」
- **THEN** 通过 git log 可查到完整变更历史，且可 git revert 撤销
