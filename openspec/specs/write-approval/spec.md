# write-approval

## Purpose

定义记忆写入的完整流程：脚本校验（硬闸门）、大模型软判断（体检出报告）、人审批（分级裁决），以及红线（密钥类）的硬拦截。核心原则：

1. **要不要人审批，由代码写死的分级规则决定，不由大模型自行拍板。**
2. **大模型只做「软判断」**——对每条候选打一个结构化体检报告（冲突 / 缺失 / 重要性 / 置信度），并给出建议等级；最终落哪个等级由代码按固定阈值裁决。
3. 写入标注「谁写的、什么时候写的」。

## Requirements

### Requirement: 三级审批流程

每次写入记忆 SHALL 经过「脚本 → 大模型软判断 → 分级裁决」三级流程，审批强度随风险递增。

#### Scenario: 写入一条新记忆
- **WHEN** 宿主提交一条新记忆
- **THEN** 依次经过：
  - 第一审（脚本）：格式校验 + 红线形状硬拦，命中即打回，不问人
  - 第二审（大模型软判断）：产出结构化体检报告（见「六个升级触发器」），只报告、不落库、不裁决
  - 第三审（分级裁决）：代码按阈值把候选落入 L0 / L1 / L2 三个等级之一

### Requirement: 六个升级触发器

大模型的软判断 SHALL 覆盖六个升级触发器，任一项命中即抬高候选的风险等级。

#### Scenario: 识别升级信号
- **WHEN** 候选命中以下任一信号
- **THEN** 大模型在体检报告中标注对应字段：
  - `conflict`：与库里已有结论互相矛盾
  - `high_impact`：高影响 / 不可逆（删除、作废被多处引用的核心结论）
  - `ambiguous`：输入本身歧义或自相矛盾
  - `novel_type`：出现未定义过的记忆类型
  - `compliance`：疑似触碰合规 / 隐私边界（脚本未拦但可疑）
  - `uncertain`：推理链中明确出现「可能 / 也许 / 例外」等不确定表述

### Requirement: 三级裁决（L0 / L1 / L2）

大模型报告 SHALL 由代码按固定阈值映射为三个等级，而非由大模型直接决定。L0 静默自动入库；L1 / L2 进入待审队列异步确认，L1 由用户批量审批、L2 强制人工逐条拍板。

#### Scenario: L0 自动入库

- **WHEN** 脚本通过、且大模型判定无冲突、无缺失、低重要、高置信
- **THEN** 直接写入，事后留审计，不提示用户、不打断对话

#### Scenario: L1 需人确认

- **WHEN** 命中任一触发器（冲突 / 缺关键信息 / 中重要 / 中置信）
- **THEN** 生成候选进入待审队列（状态 pending），用户可异步批量批准或驳回，不阻塞对话

#### Scenario: L2 强制人工

- **WHEN** 高影响 / 碰合规边界 / 删除或作废已有结论 / 低置信
- **THEN** 进入待审队列并标为高优先级，必须用户逐条拍板，不批不入库

### Requirement: 大模型软判断暂留接口，接 LLM 为后续诉求

v1 阶段 SHALL 只预留大模型软判断的接口与结构化报告格式，用规则产出报告跑通流程；v1.1 SHALL 把该接口升级为可插拔 LLM 提炼器，接入真实 LLM 做第二审，但裁决仍由代码按固定阈值完成，LLM 不自行拍板要不要人。

#### Scenario: v1 用规则产出体检报告
- **WHEN** v1 阶段需要产出一条候选的体检报告
- **THEN** 由代码规则生成报告（冲突用显式关联字段近似判断），不调用真实 LLM

#### Scenario: v1.1 接入真实 LLM
- **WHEN** 后续接入 LLM
- **THEN** 大模型按同一套结构化报告格式产出软判断，代码仍按固定阈值裁决，不因接 LLM 而让模型自行拍板

#### Scenario: 可插拔 LLM 提炼器

- **WHEN** 宿主配置了 LLM 接入信息（base_url / model / key）
- **THEN** 写入时由 LLM 按结构化体检报告格式产出软判断，覆盖六个升级触发器与 importance / confidence / missing 字段

#### Scenario: LLM 不可用时降级

- **WHEN** LLM 未配置、网络失败或返回不可解析结果
- **THEN** 系统 MUST 退回 v1 的规则体检报告，流程照常，不阻断写入

#### Scenario: 裁决仍归代码

- **WHEN** LLM 产出了软判断报告
- **THEN** 代码 MUST 按固定阈值把报告映射为 L0 / L1 / L2，MUST NOT 让 LLM 直接决定是否需要人审批

### Requirement: 第一审脚本校验

格式校验与红线拦截 SHALL 由纯代码完成，零模型调用。

#### Scenario: 格式错误被拦截
- **WHEN** 写入的记忆字段含非法值（如换行注入 frontmatter、日期非 ISO 8601、invalid_at 早于 valid_from）
- **THEN** 脚本 MUST 拒绝写入并报错，不依赖大模型自觉

### Requirement: 密钥类红线硬拦

形状规则红线 SHALL 覆盖「凭据与密钥类」及「机器可读标识符类」两类内容，在写入前由纯代码完成匹配与处置，不依赖语义判断或大模型。凭据与密钥类 SHALL 强制打码；机器可读标识符类 SHALL 默认告警、打码可配置；叙述性私人事实 SHALL NOT 被形状规则拦截。命中记录 SHALL 只标注规则编号，SHALL NOT 记录原值。

#### Scenario: 密钥形状被拦截

- **WHEN** 写入内容包含已知厂商密钥前缀、私钥块、三段式令牌、带凭据的连接串、通用密钥赋值或高熵串
- **THEN** 系统 MUST 在写入前把命中片段替换为打码占位，并在审计记录中标注命中的规则编号，MUST NOT 记录原值

#### Scenario: 机器可读标识符被识别

- **WHEN** 写入内容包含带校验和的卡号、IBAN、邮箱、手机号、IP（v4/v6）、MAC、UUID、加密货币地址或 URL 中的凭据参数
- **THEN** 系统 SHALL 给出告警并按配置决定是否打码，且 MUST NOT 因告警拒绝整条记忆

#### Scenario: 误报被抑制

- **WHEN** 命中形状的内容校验和不通过，或已列入误报白名单
- **THEN** 系统 SHALL 不产生拦截或告警，记忆照常入库

#### Scenario: 叙述性私人事实不进红线

- **WHEN** 写入内容是不愿对外公开的私人敏感事实（如个人经历、家庭情况等）
- **THEN** 形状规则 MUST NOT 拦截，该内容照常入库，对外口径由输出策略层负责

### Requirement: 是否要人审批由代码分级规则决定

「哪些操作需要人审批」SHALL 由代码写死的分级规则决定，不由大模型临时决定。

#### Scenario: 确定性操作自动完成
- **WHEN** 操作属于确定性整理（改日期格式、调权重、加链接、去重、目录归类）
- **THEN** 脚本自动完成，零审批

#### Scenario: 内容变更必须审批
- **WHEN** 操作属于内容变更（合并、拆分、取代、删除、改摘要）
- **THEN** 必须作为「提案」交给裁决者审批，接受才生效
- **AND** 每种操作有数量上限，防止一次误批一大片

### Requirement: 敏感事实可入库，输出策略分层

不愿对外公开的私人敏感事实 SHALL 可正常入库，不属红线拦截范围；对外输出的口径随「对方是谁 + 场景」变化，由独立的输出策略层控制。

#### Scenario: 敏感事实入库
- **WHEN** 写入不愿对外公开的私人敏感事实（如个人经历、家庭情况等）
- **THEN** 系统 MUST NOT 拦截（这些不是密钥类红线）
- **AND** 照常入库，作为「对用户完整了解」的一部分

#### Scenario: 输出口径随人随场景变（v1 后细化）
- **WHEN** 需要对外输出某敏感事实
- **THEN** 输出口径由输出策略层按「对方是谁 + 什么场景」选择
- **AND** 该输出策略层是 v1 之后需专门设计的方向，本规范只挂起约束、不写死实现

### Requirement: 写入可追溯与可撤销

每次写入 SHALL 标注来源（author）与时间（created/updated），且任何写入都可撤销。

#### Scenario: 撤销一次写入
- **WHEN** 用户需要撤销某次写入
- **THEN** 系统 MUST 能回退该次写入（借助 git 或等效机制），不留半残状态

### Requirement: 冲突检测增强

LLM 软判断 SHALL 在写入时把候选与检索出的相似已有结论做比较，显式判断 ADD / UPDATE / SUPERSEDE / NOOP，并与时间轴（invalid_at / superseded_by）联动。

#### Scenario: 冲突显式判定

- **WHEN** 候选与库中已有结论存在矛盾或重叠
- **THEN** LLM 在体检报告的 conflict 字段标注冲突对象与建议操作（UPDATE / SUPERSEDE / NOOP），供代码与后续人审批参考

### Requirement: 待审队列审批形态

除 L0 静默入库外，L1/L2 候选 SHALL 走「待审队列 + 异步确认」路径：写入前征得用户明确同意；用户长期未处理 SHALL 降级暂存到 archive 冷存储而非静默丢弃。

#### Scenario: 明确同意后写入

- **WHEN** 用户对某条待审候选明确同意
- **THEN** 系统 SHALL 写入真相源并从待审队列移除

#### Scenario: 超时降级暂存

- **WHEN** 待审候选超过配置时限（默认 7 天）未被处理
- **THEN** 系统 SHALL 将其移至 archive 冷存储，保留完整内容，可恢复，SHALL NOT 静默删除
